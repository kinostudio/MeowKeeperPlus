# CUDA 有效吞吐與降階診斷（2026-10-19，尚未全部驗收）

> 本文含正式主機實測資料，僅供本機工作紀錄；不得放入公開程式包或推送至公開 GitHub。逐樣本 GPU benchmark JSON 亦只留在被忽略的 `data/diagnostics/`。

## 正式 Host 快照，不是持續推論基線

本節首段是 Dashboard 重新登入前的歷史快照：SHRIMP-ASUS 正式 r107 當時為 `suspended`、worker不存活、AI FPS=0，來源約4.94 FPS；最後觸發為640／1 FPS時平均1249.7 ms大於1000 ms預算、GPU負載11%、52°C。不能把它當作後續現況；登入後較新唯讀數據見本文「後續遠端唯讀複核」。

## 已釐清的定義與程式問題

- `AdaptiveAnalyzer.measured_fps()` 為最近5秒「完成且未略過」的分析數除以5；不是模型單次延遲倒數，也不是來源FPS。
- `analysis_end_to_end` 計時在同步GPU／CPU採樣之後才開始；它包含adapter、worker IPC、解碼、模型、追蹤及其他同步Host分析工作，但不包含取下一張影格等待與外部採樣。不能只用其平均值反推整條管線吞吐。
- GPU 0可以是真正的有效瞬間值，不是CUDA失敗證據；NVIDIA採樣失敗回None。NVIDIA `utilization.gpu` 表示採樣期間至少有一個 kernel 執行的時間比例，不是 MeowKeeper+ 專屬比例；Windows WDDM 下 NVML 每程序 VRAM 可能回報 unavailable，需顯示 unavailable，不以整卡 VRAM 假稱程序用量。舊UI的歷史reason會一直顯示，不能當作目前仍超時。
- GPU API原本在分析呼叫路徑同步執行`nvidia-smi`；實機閒置查詢10次平均358.01 ms，穩態314.9～334.4 ms，首次681 ms。對照推論負載下查詢平均約65.94 ms，成本受狀態影響，不將閒置358 ms當作推論中的固定成本。

## 已實裝，未部署

### 0.8 FPS 的可重現機制

使用5 FPS來源時間線、外層3 FPS與內層安靜1 FPS，原本兩層獨立的「距上次允許時間」閘門會讓內層只能在0、1.2、2.4秒等時點分析。10秒模擬後，最近5秒完成數為4，`measured_fps()`顯示0.8。新增回歸在修復前確實失敗（0.8 != 1.0）。

已修正為：內層活動採樣比外層安全上限更低或相等時，不先做另一層丟棄；內層仍照原規則限制。外層安全上限更低時，外層仍強制限制。修復後相同時間線為1.0 FPS，另驗證活動5 FPS／安全1 FPS時不超過1 FPS。這不是將安靜模式強迫升到3或5 FPS，也不是繞過負載保護。

**這證明程式存在足以造成0.8 FPS的機制，不代表已取得當時正式Host的安靜模式狀態。** 新狀態提供活動採樣與共同上限；正式工作階段登入後仍需核對。

另發現HIGH偵測與LOW身分工作共用不可搶占的單工作者排程：正在執行的LOW工作仍可能讓HIGH等待。先加入按優先級的排隊／執行區間分布，不未經量測就平行啟動多個GPU模型。

- 每個分析器一個背景快取、最多一個查詢在途，保持原2秒採樣與6秒過期；不因每個觀看者啟動新採樣。關閉失效快取，不改驅動、GPU時脈或自動升階。
- 保留單一最新影格佇列；加入來源等待、佇列停留／丟幀及有界分布，未知FFmpeg解碼縮放時間保留None。
- worker提供JPEG解碼、輸入準備、同步模型輸出取得、CPU fallback、後處理／追蹤、RPC傳送／往返等耗時。平均、P50、P95和筆數有界保存。各程序只量自身單調時鐘區間，不相減跨程序絕對時間；RPC差值包含排程與序列化，不是純IPC或純GPU kernel耗時。
- 暖機provider節點證據會回傳；fallback後清空舊CUDA證據。不是每張都開profiling。
- 降階觸發保存當時／之後上限、預算、平均／P95、負載、溫度及UTC／單調時間。UI分開顯示歷史原因與目前是否超時，過期樣本不裝成當前值。仍只允許手動恢復。

**對「1920 的 P95 是否比 960 低」的回答：是，最後修正過排程的三輪隔離測試仍可重現。** 但不能說1920整體更快：1920的平均總耗時94.81 ms、中位數90.49 ms，均高於960的56.87／36.80 ms；輸入準備、GPU整卡平均負載及VRAM也更高。差別是960／1280有明顯偶發長尾（模型 P95 約160 ms、最大約376～397 ms），1920分布較集中（模型 P95 84.74 ms、最大147.41 ms）。因此 P95 反轉是真的統計觀察，不等於更高解析度更省算力。修正後實際速度為4.78／4.79／4.94 FPS，而非設定上限5 FPS；完整漏掉的排程時槽2／1／0。

根因**尚未確定**：分階段模型呼叫同步取得輸出，因此所量的是呼叫完成時間，不是純 CUDA kernel 時間；整卡 GPU／時脈／功率每約2秒取樣，不能精確對齊單張慢樣本，也不能歸屬到 MeowKeeper+。此證據無法分辨低尺寸長尾來自 CUDA／驅動排程、CPU／OS 排程或其他背景負載；不應以猜測改正式 AI 上限。3個尺寸在此 RTX 2060 的實際吞吐約4.78～4.94 FPS，GPU整卡平均低於40%軟目標，峰值溫度不超過67°C；這不外推至 MX250，也不驗收長期負載。

provider 觀測仍為 CUDAExecutionProvider 308 節點、CPUExecutionProvider 55 節點；CPU worker 正規化平均約1.85／2.18／3.03%，不是純 GPU 全接管。目標 MX250、真實來源完整 pipeline（來源等待、worker IPC、追蹤、事件與 Telegram）及長期穩定性均 `not_checked`。正式 r107 未含此批新增接線，未重啟／修改正式 Host、未提高溫度門檻、未手動恢復 AI、未建置或發布。
