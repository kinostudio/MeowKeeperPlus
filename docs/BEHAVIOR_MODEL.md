## 受控回饋學習（2026-10-09；r72 已安裝，本輪通知修正尚未部署）

逐軌跡、已確認的單貓裁切可擴充獨立身分特徵庫；衝突／否定回報會撤回樣本。
行為標籤僅供評估，不自動修改規則或重訓。完整邊界與驗收見 [FEEDBACK_INCREMENTAL_LEARNING.md](FEEDBACK_INCREMENTAL_LEARNING.md)。

## 1. 為何拆成三個維度

「玩耍」描述行為目的；「跑動」描述動作強度；「追逐」描述一個可重疊事件。若混在同一列舉，快速前往飯碗或受驚逃跑都會被錯算成玩耍。

因此每隻寵物同一時刻保存：

1. 一個主要行為 `behavior_state`。
2. 一個動作狀態 `motion_state`。
3. 零到多個附加事件 `event_tags`。

## 2. 主要行為

| 值 | 使用者顯示 | 定義 |
|---|---|---|
| `sleeping` | 睡眠 | 具休息姿態、低動作且持續達睡眠門檻 |
| `resting` | 休息 | 低動作但尚未達睡眠條件 |
| `eating` | 進食 | 飯碗區、頭部位置、停留與動作規則符合 |
| `drinking` | 喝水 | 飲水區、頭部位置與停留規則符合 |
| `playing` | 玩耍 | 具遊戲情境、玩具或互動等證據 |
| `grooming` | 理毛 | 重複舔舐或整理動作符合 |
| `litter_box` | 使用貓砂 | 貓砂區與停留／姿勢條件符合 |
| `other_active` | 其他活動 | 可見且活動中，但無更明確主要行為 |
| `out_of_view` | 不在畫面 | 已知寵物未被攝影機看見 |
| `unknown` | 無法辨識 | 看見候選目標但證據不足或身分不確定 |

所有門檻都屬於設定 profile，不得寫死在判斷器各處。

V0.2 的初始規則由 `BehaviorConfig` 集中管理：進食至少 10 秒、飲水至少 5 秒、睡眠至少
60 秒、狀態切換 hysteresis 2 秒；用餐與飲水的中斷合併時間分別為 30 秒與 20 秒。這些
只是可校正起點，不是家庭貓咪的通用真值。

## 3. 動作狀態

| 值 | 使用者顯示 | 說明 |
|---|---|---|
| `stationary` | 靜止 | 位移低於靜止門檻 |
| `low_motion` | 低度移動 | 有小幅姿態或位置改變 |
| `walking` | 一般行走 | 一般速度移動 |
| `running` | 快速跑動 | 速度或加速度超過門檻 |
| `jumping` | 跳躍 | 相對身長的垂直位移與時序特徵符合 |

`running` 可與 `playing`、`other_active` 或其他主要行為並存，不能直接映射為玩耍。

## 4. 附加事件

| 值 | 使用者顯示 |
|---|---|
| `chasing` | 追逐 |
| `cat_interaction` | 貓咪互動 |
| `meow` | 一般貓叫 |
| `caterwaul` | 哭叫／發情叫聲 |
| `retching` | 疑似乾嘔聲 |
| `possible_vomit` | 高疑慮嘔吐 |
| `zone_enter` | 進入指定區域 |
| `zone_exit` | 離開指定區域 |

`possible_vomit` 是疑似事件，不是醫療診斷。

音視融合至少需要乾嘔音訊與視覺靜止／姿態證據同時達到門檻。只有單邊高分時保留診斷資料，
不建立疑似嘔吐候選，也不傳送醫療宣稱。

## 5. 推論與時間平滑

單影格分數不可直接建立長時間行為。建議流程：

```text
原始觀測
→ 區域／物件／姿態／音訊特徵
→ 候選分數
→ 時間平滑
→ 最短持續門檻
→ 互斥主要狀態決策
→ 事件合併
```

初始規則參考值只能放在版本化設定 profile，需由家庭實拍資料校正。

## 6. 事件切分

進食例：

- 進入飯碗區並符合頭部接近、低速與停留條件後開始。
- 短暫離開但在 `meal_merge_gap_seconds` 內返回，合併為同一次。
- 少於 `meal_min_duration_seconds` 的候選不計正式用餐，但可保留診斷資料。

飲水採相同原則，使用獨立門檻。玩耍、理毛與貓砂也需定義最短持續與中斷合併規則。

## 7. 統計

每隻寵物分別產生：

- 各主要行為累計時間、次數、平均、最長與時段。
- 動作狀態累計與跳躍次數。
- 進食／飲水次數與單次時間。
- 與 7 日平均的差異。
- 未辨識、不在畫面、攝影機斷線與有效監控時間。

### 分母

- 占日曆時間：行為秒數除以選定日期範圍。
- 占有效監控時間：行為秒數除以該寵物可可靠觀測的時間。

`out_of_view`、`unknown`、攝影機斷線與服務停止不得算成睡眠。

多寵物統計需分別計算；家庭總覽可顯示「貓小時」或共同互動，但不得把兩隻貓時數相加再除以 24 小時。

## 8. 信心與人工閉環

### 2026-10-09 影片兩輪回饋（repository 新版，尚未部署）

已登錄兩隻寵物時，偵測影片第一輪直接提供「是〈寵物一〉」「是〈寵物二〉」
「兩隻都在」「不是貓咪」。名稱取自啟用的寵物登錄資料，不寫死。
第一輪不顯示行為；不是貓咪直接結束，不再詢問。
選一隻時詢問該寵物行為；選兩隻時依登錄順序先問第一隻，保存後再問第二隻。
行為選單僅有進食、喝水、休息、睡覺、玩耍、理毛、使用貓砂、其他活動；
不顯示「不在畫面」「無法判斷」。看不清楚時可不回覆，不強迫猜測。

SQLite schema 12 新增 `telegram_pet_reviews`、`telegram_pet_review_receipts`、
`telegram_pet_review_history`，保存可恢復步驟、送達回條與不可覆寫的逐寵物行為歷史。
兩隻各以 pet_id 保存，不互相覆寫；重複 update、舊步驟、錯誤收件者及未參與回饋
均不得新增標籤。這是影片級人工回報，不冒充 track-to-pet 配對或自動模型訓練。
原有逐軌跡回饋維持獨立事件對應；不可把「兩隻都在」硬寫到同一條 track。
舊訊息 callback 保留相容，新影片按鈕需部署新版後才會生效。

驗證：完整回歸 419 tests 通過（127.447 秒）；其後補充第二階段傳送失敗恢復案例，
兩輪精靈 7 tests 與 Telegram 接線 17 tests 通過，Ruff、compileall 通過。
沒有向正式 Telegram 發送本輪新版測試或修改正式 SQLite；目前安裝的 r71
不含此變更，不能以既有 Telegram 訊息宣稱新兩輪流程已完成真實部署驗收。

### 2026-09-27 統計查閱入口

`/analytics` 與受登入保護的 `/api/v1/analytics/behavior` 已接入 SQLite 已保存行為，
查詢需提供含時區的 start/end，最多 31 天、10,000 筆；不修改事件或啟動模型。
跨日事件依範圍裁切，分別顯示期間內開始次數、相交事件數與範圍內平均時長。
未結束事件只列 pending，不推算結束時間；重疊區間停用百分比。
未知身分按獨立 track 分組，不合併成一隻已知貓；此分組仍非永久個體辨識。
目前只提供日曆分母；有效監控分母尚未建立，不顯示偽造比例。
這是 experimental 查閱入口，尚不代表正式 Host 已接入 V0.2 或家庭行為準確率通過。
21 項相關統計／Web／Tray 測試、Ruff、語法檢查通過；尚未部署到 r16／r17。

每筆行為保存：

- `raw_confidence`
- `calibrated_confidence`（未校正時為 null）
- `inference_method`
- `model_version`
- `rule_profile_version`
- `camera_preset`
- `human_review`

Telegram 回饋可標記正確寵物、正確行為、誤判或無法判斷。累積資料用於門檻校正與未來訓練；不在背景中未經審核自動重訓模型。

### Telegram 個體／行為回饋的目前接線

回饋由每位已授權的私人 Telegram 使用者自行選擇，預設不參與。`/feedback on` 開啟、`/feedback off` 退出、`/feedback status` 查詢；設定即時生效並持久保存，不影響該使用者是否收到貓咪告警或靜音設定。只有參與者收到的真實偵測器 `cat_detected` 圖片／影片會附「是貓咪／不是貓咪」按鈕；退出後舊訊息上的回饋按鈕亦不再接受。參與者按「是貓咪」後，Bot 另送兩組獨立按鈕：

- 個體：從本機 `data/pets` 登錄檔動態列出最多八隻啟用的寵物，另有「身分不確定」。未登錄時不猜測名稱。
- 行為：進食、喝水、休息、睡覺、玩耍、理毛、使用貓砂、其他活動、無法判斷。這是人工標註選項，不代表現有模型都能自動辨識。

個體與行為各可獨立更正；目前值保存在 `media_event_annotations`，每次選擇另記入不可覆寫的 history。改回「不是貓咪」會撤銷該回覆者的目前細項標註，但歷史仍保留。這些標註不直接更改模型推論、事件影片或行為統計，也不自動收集影格訓練。啟用真實個體推論前，需以家庭攝影機中的該貓參考影像建立已校驗 DINOv2 特徵；Dashboard 的「寵物身分登錄」頁面現在可保存 JPG 參考照片並在背景建立特徵，`tools/enroll_pet.py` 仍可供維護者批次使用。家庭準確率驗收仍待完成。

「建立特徵」不等於重新訓練模型：它只對新照片做一次 embedding，工作量大致隨照片張數增加，可在背景執行，GPU 不可用時仍可用 CPU 但會較慢。自動微調 YOLO 或 DINOv2 則需要整理已標註資料、訓練／驗證切分、模型版本與回退機制，可能長時間占用 GPU／CPU，也可能過度適應單一家庭場景；目前不自動執行此操作。

### Telegram 逐貓摘要與逐軌跡回報

啟用 V0.2 分析且 Telegram 通知已啟用時，已完成／切分的行為事件會以一則摘要列出當時可見的多條軌跡，例如「嗨啵｜其他活動／行走」及「Saki｜進食／靜止」。每一列的「回報軌跡」按鈕都綁定該條已保存行為事件的 UUID；不把內部 track ID 放進訊息或 callback。摘要在行為事件完成／切分時彙整，可能等候事件合併窗口，不是每影格通知。

點選某條軌跡後，該使用者會看到只屬於那條軌跡的回報選單：先確認「是貓／不是貓」，再可選已登錄個體、主要行為（例如進食）及獨立動作狀態（例如行走）。因此「嗨啵行走」會保存在 motion 維度，不會錯塞成主要行為；選「不是貓」會清除該使用者此軌跡的目前身分、行為與動作標籤，但保留不可覆寫歷史。

逐貓摘要仍標示為實驗性候選；只有已選擇參與回饋的私人收件者會收到軌跡按鈕，通知開關／靜音仍由每位收件者各自控制。系統把送達回執綁到收件者雜湊與 Telegram message ID，再驗證私訊授權、參與偏好與該事件回執後才接受標籤。SQLite schema version 11 為動作維度增加可重複執行的 migration，保留舊標籤及歷史。自動化雙貓／雙軌跡、回執、opt-in、動作分類與 migration 測試已通過；真實 Telegram 對話的推播、按鈕點擊及正式 Host 安裝尚未驗收，家庭資料也尚未證明身分／行為準確率。

`out_of_view` 需要由追蹤生命週期與來源健康狀態產生，不能因為單一影格沒有 bbox 就當成
睡眠；`unknown` 也不得自動併入休息或睡眠統計。

## 9. V0.2B 匿名事件與延後身分

行為判斷不等待個體身分。只要 bbox、軌跡、區域與時間特徵足夠，系統可先建立：

```text
21:32:10  神秘喵喵進入飯碗區
          好像在吃喵糧哦
```

事件欄位 `pet_id` 暫時為 `null`，並保存 `identity_status`、`identity_confidence`、
`identity_model_version`。背景 DINOv2 完成後，系統更新同一 `event_id`，例如：

```text
21:32:10  嗨啵進入飯碗區
          進食事件持續 3 分 42 秒
```

更新只作用於尚未人工鎖定的事件，原始 unknown 與修正內容寫入
`identity_corrections`，不得抹除稽核歷程。`track_id` 是延後綁定的關聯鍵，不能當作
永久寵物身分。

## 10. 24H 優先規則

身分辨識不得逐影格執行；只在新 track、遮擋後、低信心或可設定複核間隔到期時排入
LOW 工作，最多保留有限 pending tasks。同一 track 的工作需去重；GPU 過載、crop
品質不足、CUDA OOM 或逾時時回傳 unknown，不能丟棄行為事件。
