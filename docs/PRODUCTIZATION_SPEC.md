## 2. 要成為什麼產品

讓普通飼主不必理解 RTSP、subtype、模型 Provider 或 Session，也能完成「連攝影機 → 偵測貓咪 → 保留事件 → Telegram 收到影片 → 必要時確認是哪隻貓」。上班不方便拿手機時，可在已驗收相容的 Apple Watch Telegram 播放通知影片；這是既有使用者驗收經驗，不保證所有手錶／編碼組合。

正式產品的價值是 **可靠保存、清楚告知、可恢復、容易操作**，不是功能越多越成熟。第一個正式版可只承諾基本找貓與事件通知，身分、行為與外部圖片分析繼續標示 experimental；不必等待所有研究題目完成才發布可靠核心。

### 2.1 1.0 核心承諾候選

1. Windows 上持續監控，瀏覽器關閉或登出不停止核心；SYSTEM 安裝模式另驗證 Windows 尚未登入時的運作。可攜版不承諾開機前監控。
2. 一個活動來源、必要的單一攝影機上游；預覽、AI、快取及通知共享資料。不同瀏覽器不能各自拉攝影機或啟動轉碼。
3. 本地 YOLO 找貓、事件 JPEG／連續 MP4、授權多收件者 Telegram；通知失敗不拖垮影音與事件落庫。
4. 安裝、升級、資料備份與復原可驗證，不因換可攜包而默認資料會自動合併。
5. 未知、離線、降級、通知失敗都顯示可操作的原因；不以 running、註冊 producer 或指令送出冒充結果。

### 2.2 不納入第一個正式版的必要承諾

任意攝影機相容、所有瀏覽器 HEVC 解碼、每台機器 1080p／5 FPS AI、醫療／異常行為診斷、全自動重訓、任意多攝影機同時分析、全自動 VPN 管理、無人值守更新。這些需各自立項、測試及決定是否交付，不作隱含承諾。

## 4. 架構與資料契約

### 4.1 媒體與資源

攝影機 → go2rtc 單一必要上游 → 本機分流給 MSE／分析影格／壓縮快取；事件與 Telegram 不受網頁休眠、登出或AI身分失敗影響。每台瀏覽器可以有輕量 consumer，不得因此多開上游或FFmpeg producer。

來源原始尺寸、影片解碼尺寸、JPEG預覽尺寸、YOLO輸入長邊、身分裁切尺寸必須分開顯示。縮放不等於重新編碼，原碼4K顯示成小視窗仍可能解碼4K。不要強制三種分析尺寸相同；以實測瓶頸決定採樣與畫質。

### 4.2 網路、安全與控制

- Dashboard 預設 loopback，區網與遠端存取為選用；所有管理頁、媒體、WebSocket及控制沿用登入／Session／CSRF契約。
- go2rtc 管理API保持本機限定；RTSP預設本機。使用者另行授權的 Private LAN RTSP 是獨立選項，會繞過Dashboard登入，不能說與登入保護等價；不默認延伸到WAN。
- Tailscale只作官方工具整合與受限已配對中繼，不由Python管理VPN或掃描任意Tailnet設備。
- PTZ按實際活動stream、裝置ID與端點配對，不按型號猜位置；短促移動、finally stop、裝置讀回，沒有座標就回報未驗證。
- 雲端分析預設關閉，目的地／模型變更須重新同意；秘密、家庭畫面及私人報告不進乾淨程式包。

### 4.3 資料與學習

SQLite保存事件、原AI證據、人工修訂與用量；pet目錄保存參考照片與版本化特徵。人工標籤不得覆寫原AI分數，候選不得偷偷成為真值。回饋特徵擴庫需同意、品質／版本檢查與去重；沒有證據不得宣稱準確率增加。

可攜版與安裝版依各自Data root讀資料，不自動掃描或合併其他版本。所謂完整備份是「產品定義的持久資料」，不含所有程式、快取或可跨帳號搬移的秘密；匯出頁必須列明包含與排除。跨版本匯入需格式版本／schema相容與失敗不破壞原資料，不能要求版本號完全相同，也不能承諾任意新舊互通。

### 5.1 AI 從 experimental 畢業的獨立門檻

- 準備家庭獨立holdout：同框多貓、夜間／逆光、遮擋、不同距離、陌生貓及人類；依事件／拍攝時段切分，避免同圖或近似影格同時用於學習與驗證。
- 個體報告至少包含各貓precision／recall、unknown率、陌生貓false-accept、track swap與雙貓身分衝突；行為分開建立人工真值及混淆矩陣。
- 先提出資料量與門檻，經核准再凍結測試；未取得足夠樣本不填假百分比。模型相似度不能直接稱為正確機率。
- 回饋可追溯、可撤回；特徵版本可比較與回退；評估通過後才切換正式候選。大量低品質特徵不是越多越好。
- 「重建特徵／重新比對」與「重訓模型權重」分開操作與說明；後者未有資料／評估／資源方案前不自動執行。

### 5.2 效能與監控驗收方法

分開測CPU、Intel、MX250；固定來源編碼／尺寸、AI尺寸／FPS、觀看者數、事件率及測試時段。記錄整機與本程式CPU／RAM、GPU／VRAM、可用溫度、磁碟讀寫／容量、分析平均／P95、影片掉幀、上游及FFmpeg數。未知感測值保持未知；不以單次15% GPU或低溫推論有剩餘推論能力。

基本基線仍為640像素級、約5 FPS目標；1080p／5 FPS是進階選項的驗收目標，不是所有硬體的保證。40%持續負載目標需說明感測器與量測分母，不藉降低至無法偵測來假裝達標。

## 6. 發布判斷與建議下一步

**目前適合定位：具備多項實機證據的工程預覽／家庭Beta候選，不是已全面驗收的正式1.0。** 主要缺口是跨版本交付、真實閉環與長時間／跨機證據。共用按需H.264 MSE已追加隔離證據；HEVC WebRTC與同次編碼失敗熱切換仍未實作，不能全部歸類成「只差驗收」。

建議下一輪只收斂P0：最新PTZ真實前後讀回 → 來源重啟與攝影機切換 → 真實事件／逐軌跡Telegram回報落庫 → 更新包runtime／安裝占用回歸。之後再開始P1／P2，不繼續無限制增加新功能。

每個待辦固定記錄：需求ID、實作入口、測試、包版本、部署版本、設備／資料根、安全遮罩證據、passed/failed/not_checked、下一步及復原方式。不採無分母的「完成90%」，也不把所有歷史測試數相加成目前覆蓋率。
